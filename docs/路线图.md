# 路线图

> 从 M0（已完成）推进到最终形态的分步落地路径。
> 使用方式：**按 M1 → M8 顺序推进，每步做完再进下一步**。每阶段都有「前置条件 / 要做的事 / 验收标准 / 产出」，验收不过不往下走。
> 返回入口：[CLAUDE.md](../CLAUDE.md) ｜ 最终形态：[设计总纲.md](设计总纲.md)

## M2｜客户端写回：建任务 / 完成 / 延期 + 增量同步（已完成）

**目标**：客户端不再只读，能新建、完成、延期任务，且与飞书双向一致。

**已完成内容**

| 模块           | 文件                                                        | 说明                                                                                                                                                      |
| -------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 飞书写接口     | [client.py](../client_windows/app/feishu/client.py)         | 新增 `create_record` / `update_record` / `get_record` / `search_records`                                                                                  |
| 仓储写接口     | [repository.py](../client_windows/app/feishu/repository.py) | `build_create_fields` / `build_complete_fields` / `build_defer_fields` / `find_by_external_id` / `create_task` / `update_task` / `get_remote_modified_ms` |
| 同步服务       | [sync.py](../client_windows/app/services/sync.py)           | 推送离线队列 + 全量/增量拉取 + 冲突检测                                                                                                                   |
| 离线队列       | [cache.py](../client_windows/app/services/cache.py)         | `pending_ops` 表 + `enqueue_op` / `list_pending_ops` / `delete_op` / `set_op_force`                                                                       |
| 新建任务对话框 | [task_dialog.py](../client_windows/app/ui/task_dialog.py)   | 任务名/截止时间/优先级/类型/预计耗时/描述                                                                                                                 |
| 主窗口写操作   | [main_window.py](../client_windows/app/ui/main_window.py)   | 「新建任务」「完成」「延期」按钮 + 延期菜单                                                                                                               |
| 总控接线       | [main.py](../client_windows/app/main.py)                    | 写操作入队 + 乐观更新 + 后台推送 + 冲突弹窗                                                                                                               |

**关键设计**

- **统一入队**：新建/完成/延期都先写 `pending_ops` 表，再由后台线程按序推送，断网不丢。
- **幂等**：`create` 推送前按 `外部ID` 查重；`complete/defer` 的 PUT 本身幂等。
- **乐观更新**：complete/defer 入队后立即更新本地缓存，界面即时反馈；create 则等推送成功+增量拉取后再显示。
- **冲突检测**：推送前比较 `base_ms`（入队时的云端修改时间）与实时云端修改时间，不一致则弹窗让用户决定覆盖或放弃。
- **增量游标**：`sync_meta.pull_cursor_ms` 记录上次拉到的最大修改时间；定时器走 `search(修改时间 > cursor)`，失败回退全量。

### 验收标准

- [x] 客户端新建任务，10 秒内飞书表格出现该记录。
- [x] 客户端点「完成」，飞书状态变为已完成且完成时间被填。
- [x] 手机在飞书改一条任务后，客户端下一轮同步可见。
- [x] 拔网线建 3 条任务，恢复网络后 3 条都自动补交且无重复。
- [x] 反复点「完成」不会重复写入。

> 验收在合并本阶段改动后由真机/真表操作完成。

## M3｜AI 拆解 + 优先级建议

> **轻量化替代**：手机端的 AI 拆解可由飞书豆包工作 agent 直接完成（见 [豆包agent轻量化方案.md](豆包agent轻量化方案.md)）。本阶段的客户端 AI 拆解可**降级为可选**，或直接跳过——手机端用豆包，PC 端用客户端写回（M2）手动建任务即可。

**目标**：一句话 → 结构化任务；大任务 → 子任务 + 检查清单；给出排序建议。

### 前置条件

- M2 通过。
- 已注册 DeepSeek 开放平台并拿到 API Key，充值少量额度。

### 要做的事

1. **Provider 层** `app/ai/provider.py`：`LLMProvider` 接口 + `DeepSeekProvider`，预留通义/智谱实现位。
2. **提示词** `app/ai/prompts.py`：解析提示词、拆解提示词，**硬编码学术诚信边界**。
3. **解析与校验** `app/ai/parser.py`：JSON 解析 + Schema 校验 + 失败重试 1 次 + 兜底（只取标题）。
4. **置信度策略**：`confidence < 阈值(0.6)` → 写入「收集箱」并标注待确认，不自动定优先级。
5. **写回**：解析结果写入任务表；`subtasks` 写入子任务表并关联主任务。
6. **AI 建议（只建议不自动改）**：输出建议文本，客户端一键采纳 / 忽略。
7. **成本控制**：只在「新建 / 手动拆解 / 手动请求建议」时调用，不做定时轮询。
8. **UI**：「一句话添加任务」输入框 +「AI 拆解此任务」按钮 + 建议展示区。
9. **更新文档**：`docs/API.md` 增加 AI 模块说明与输出契约。

### 验收标准

- [ ] 输入「明天下午交高数作业」，生成含截止时间、优先级、类型、子任务、检查清单的记录。
- [ ] 输入模糊内容（如「那个东西」），`confidence` 低时进收集箱且不瞎猜优先级。
- [ ] 断网或 Key 错误时，退化为「只取标题」的规则结果，程序不崩。
- [ ] 记录每次 token 用量，单次解析成本可接受。

## M4｜娱乐监督 + 浏览器扩展 + 番茄钟

**目标**：检测抖音/娱乐网站，按 L1→L4 升级提醒；番茄钟自动累计实际耗时。

### 前置条件

- M1 的提醒模块可用。
- 已确定监督强度上限（见 [设计总纲.md](设计总纲.md) 第 8 节）。

### 要做的事

1. **进程监控** `app/services/monitor.py`：`psutil` + `pywin32`，每 5 秒采样，监控名单从设置表读取。
2. **本地 API** `app/local_api.py`：`POST http://127.0.0.1:8765/report`，接收扩展上报的 `{domain, title, seconds}`。
3. **浏览器扩展** `extension/`（MV3）：统计域名与停留时长，达阈值时上报本地 API，不采集页面内容。
4. **四级升级**：按设置表阈值（默认 10/20/30/45 分钟）依次触发 通知 → 语音 → 飞书卡片 → 全屏遮罩。
5. **豁免机制**：白名单、每日豁免次数、番茄钟休息期；豁免期内只记录不提醒。
6. **聚合写入日志表**：一次会话结束写一条，含持续时长、触发级别、处理动作、是否豁免；超 30 天按月归档。
7. **番茄钟** `app/services/pomodoro.py`：默认 25/5，可绑定任务，结束自动累加「实际耗时」。
8. **更新文档**：`README.md` 说明扩展安装与监督机制；`docs/API.md` 记录本地 API。

### 验收标准

- [ ] 打开抖音 10 分钟收到通知，20 分钟有语音，30 分钟飞书收到卡片。
- [ ] 关闭娱乐程序后，日志表出现**一条**聚合记录，且持续时长正确。
- [ ] 白名单内的程序不会被提醒。
- [ ] 番茄钟跑完 25 分钟，绑定任务的实际耗时增加 25。
- [ ] 后台 CPU 仍低于 1%。

## M5｜飞书机器人（手机可用）

> **完全替代**：本阶段可由飞书豆包工作 agent 直接实现，无需自建机器人。详见 [豆包agent轻量化方案.md](豆包agent轻量化方案.md)。如采用豆包方案，本阶段可**整段跳过**。

**目标**：手机发消息就能建任务、查今日、勾完成；客户端关机也能收到飞书提醒。

### 前置条件

- 飞书应用已开通机器人能力与 `im:message` 权限。
- 已配置事件订阅（长连接或 webhook）。

### 要做的事

1. **指令解析**：`/today`、`/add`、`/done`、`/defer`、`/review`、`/focus`（见 [设计总纲.md](设计总纲.md) 5.5）。
2. **机器人服务** `server/app/bot.py`（可先本机跑）：长连接接收消息事件；`/add` 复用 M3 的 AI 解析后写入任务表。
3. **提醒卡片**：截止提醒改为交互式卡片，按钮 `完成 / 延后1天 / 改到今晚 / 设为今天青蛙`。
4. **卡片回调**：`card.action.trigger` → 更新任务表状态。
5. **幂等**：同一消息重复回调不得重复建任务（用 message_id 作幂等键）。
6. **更新文档**：`docs/API.md` 增加机器人与卡片回调；`README.md` 写手机使用方法。

### 验收标准

- [ ] 手机上发「/add 后天组会汇报」，任务表新增记录。
- [ ] 收到提醒卡片后点「完成」，飞书表格状态变更、客户端同步可见。
- [ ] 同一条消息重复推送不会重复建任务。
- [ ] `/today` 能返回今日任务与三只青蛙。

## M6｜Linux 服务器 24h 无人值守

> **简化说明**：采用豆包方案后，服务器不再需要机器人长连接和 AI 编排模块，职责简化为**定时调度 + 统计计算**。本阶段开发量大幅降低，可推迟到确实需要「关机也能自动推提醒」时再做。

**目标**：把定时提醒、复盘生成搬到服务器，实现电脑关机也能工作。

### 前置条件

- 有 Linux 服务器（1C1G 起）。
- 有域名（webhook 需 HTTPS）或改用长连接模式免公网。

### 要做的事

1. **部署** `deploy/docker-compose.yml`：服务端容器 + 环境变量注入密钥。
2. **保活**：systemd 或 Docker `restart: always`。
3. **定时调度** `server/app/scheduler.py`（APScheduler）：
   - 每日 08:00 推送今日议程；
   - 截止前提醒 + 升级提醒（错过 30 分钟后升级，最多 3 次）；
   - 每日 22:00 触发复盘生成（AI 文本可调用豆包或 DeepSeek）；
   - 每日凌晨挑选三只青蛙。
4. **去重**：用「提醒状态」字段防重复提醒；`完成时间` 一填即停。
5. **统计服务** `server/app/services/review.py`：完成率、延期 Top3、娱乐 vs 专注时长（供复盘使用）。
6. **分工确认**：服务器不负责娱乐监控、本地语音、机器人对话（后两者分别由客户端和豆包承担）。
7. **更新文档**：`README.md` 增加部署步骤；`docs/API.md` 增加服务端接口。

### 验收标准

- [ ] 关闭个人电脑，服务器仍按时推送飞书提醒。
- [ ] 服务重启后不重复推送已提醒过的任务。
- [ ] 服务器内存占用 < 400 MB。
- [ ] 修改任务后 1 分钟内服务器下一次调度使用最新数据。

## M7｜复盘统计 + 公式字段

**目标**：飞书公式字段生效，客户端/服务器自动生成日/周复盘。

### 前置条件

- M2/M4 数据已积累至少 1~2 周。

### 要做的事

1. **飞书公式字段**：任务表 `优先级分数` / `是否逾期` / `剩余天数`；每日复盘表 `完成率`；目标项目表 `进度`。
2. **统计服务** `app/services/review.py`：完成率、延期原因 Top3、娱乐时长 vs 专注时长、青蛙完成数。
3. **AI 复盘**：统计数据 → 生成复盘报告，写入每日复盘表 `AI复盘`；用「明日重点已生成」复选框防重复。
   - AI 复盘文本可由豆包 agent 生成（手动触发或服务器调度触发），也可由服务器调用 DeepSeek 生成。
4. **周报**：每周日生成一次周复盘（完成率、拖延模式、下周建议）。
5. **可视化**：客户端加「复盘」页，展示近 7/30 天趋势。
6. **更新文档**：`README.md` 说明复盘机制；`docs/API.md` 增加统计接口与公式字段清单。

### 验收标准

- [ ] 任务表「优先级分数」公式列有值且排序合理。
- [ ] 每日 22:00 自动生成复盘内容，且不会重复生成。
- [ ] 周报能指出本周延期原因 Top3。
- [ ] 客户端复盘页能展示近 7 天完成率曲线。

## M8｜进阶：日历时间块、自动排布

**目标**：从「待办清单」升级为「时间块日程」，与飞书日历双向同步。

### 前置条件

- M6 服务器稳定运行。
- 明确课程表来源（见 [设计总纲.md](设计总纲.md) 第 8 节）。

### 要做的事

1. **时间块模型**：新增 `时间块` 概念（新表或复用飞书日历）。
2. **飞书日历接入**：读写日程事件，`time_block` ↔ 日历事件双向同步（用 external_id 去重）。
3. **自动排布**：按优先级、预计耗时、精力需求塞进空闲时段；上课/会议不占用。
4. **客户端展示**：日程时间轴视图 + 拖拽调整。
5. **回写**：排布结果推送到飞书日历，手机可见。
6. **更新文档**：`README.md`、`docs/API.md`。

### 验收标准

- [ ] 一条 2 小时任务能自动排进今天空闲时段，且不与课程冲突。
- [ ] 飞书日历上能看到自动排布的时间块。
- [ ] 在飞书日历手动拖动后，客户端能同步新时间。
- [ ] 有更紧急任务插入时，可一键重排。

## 每阶段的固定动作（重要）

1. **开工前**：确认前置条件全部满足，尤其是飞书权限与字段是否已存在。
2. **开工中**：所有密钥只进 `.env`，确保 `.gitignore` 已包含 `.env`、`data/*.db`。
3. **收工后必做**：更新 `README.md` 与 `docs/API.md`；涉及架构/数据模型/里程碑时同步更新 `docs/` 下其余文档。
4. **每阶段结束**：对照验收清单逐条打勾，不通过不进入下一阶段。
